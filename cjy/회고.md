## 1. 겪은 문제와 해결

### 문제 1. Graylog 중복 탐지
- **문제:** 하나의 공격에 대해 같은 경보가 여러 번 생기거나(같은 사건 중복), 서로 다른 이벤트가 겹쳐서 탐지되는 경우가 있었다.
- **원인:** Graylog 이벤트 정의의 **검색 시간 범위(Search within the last)**, **실행 주기(Execute search every)**, **grace period** 설정이 서로 맞지 않았다. 검색 범위가 실행 주기보다 길면 같은 로그가 매 실행마다 다시 집계되고, grace period는 알림(webhook)만 억제할 뿐 경보 생성 자체는 막지 못한다는 점을 처음엔 몰랐다.
- **해결:** `every ≤ within`, `grace > within` 원칙으로 각 규칙의 값을 다시 맞췄다. 한 공격당 생기는 경보 수가 대략 `범위 ÷ 주기`라는 것을 파악하고, 예로 P1(반복 로그인)은 범위 10분은 유지하되 실행 주기를 1분 → 2~5분으로 늘렸다.
- **결과:** 공격 1회당 Graylog 경보가 약 10건에서 2~3건 수준으로 줄었고, n8n으로 가는 알림·티켓은 grace period로 1건으로 묶였다. 세부 기준은 [graylog-setup.md 9장](HowToSetUp/graylog-setup.md#9-within--every--grace-정하기)에 정리했다. 남은 규칙들도 같은 기준으로 계속 다듬을 예정이다.

### 문제 2. 보안 이벤트 시연 미숙 · 시연 불가 이벤트
- **문제:** 리허설 때 보안 이벤트 시연이 매끄럽지 못했고(수동 조작 위주), 백엔드 설계상 **실제 공격으로는 발생시킬 수 없는 이벤트**가 있었다. 예를 들어 비정상 ADMIN 권한 승급(K6-B)은 앱이 등급 변경을 정상 사유로만 기록해서 공격으로 재현할 수 없었다.
- **원인:** 시연을 손으로 하나씩 조작하다 보니 순서가 꼬이거나 시간이 오래 걸렸고, 일부 이벤트는 앱 로직상 트리거할 방법 자체가 없었다.
- **해결:** 리허설 피드백을 반영해 **이벤트별로 번호만 입력하면 공격을 재현하는 트리거 스크립트**(`attack_trigger/bastionpay_targeted_triggers.sh`)를 만들었다. 실제 요청으로 재현되는 이벤트는 웹에 직접 요청을 보내고, 공격으로 만들 수 없는 이벤트(K6-B)는 **"내부 장악을 가정한 모의 로그"를 Graylog에 직접 주입**하는 방식으로 시연할 수 있게 했다.
- **결과:** 시나리오 6종을 메뉴 번호 하나로 재현할 수 있게 됐고, 시연 불가였던 K6-B까지 CRITICAL 티켓 + Telegram + 권한 회수·계정 잠금 흐름을 보여 줄 수 있었다. 사용법과 시나리오별 공격·탐지·복구는 [attack_trigger/README.md](attack_trigger/README.md)에 정리했다.

### 문제 3. 티켓 등급이 의도와 다르게 나옴
- **문제:** Graylog에서 MEDIUM으로 보낸 경보가 인시던트 티켓에서는 HIGH로 바뀌어 나왔다.
- **원인:** 웹 백엔드(`IncidentService`)가 n8n(Graylog)이 보낸 등급을 무시하고, 같은 출발지 IP의 이벤트 중 **가장 높은 등급으로 덮어쓰고** 있었다. 로그인 반복 실패로 계정이 잠기면 ACCOUNT_LOCKED(HIGH)가 섞여 티켓이 HIGH가 됐다.
- **해결:** 티켓 등급이 **Graylog에서 보낸 severity를 그대로 따르도록** 백엔드 로직을 수정했다(원본은 백업 후 변경, 컴파일 확인).
- **결과:** 새로 생기는 티켓은 Graylog 설정 등급을 따른다. 다만 **이미 열려 있는 티켓은 등급이 올라가기만 하고 내려가지 않는** 부분이 남아 있어, 시나리오별로 정확히 보려면 트리거 사이에 티켓을 종료하는 절차를 함께 두었다.

## 2. 더 개선하고 싶은 부분

1. **등급 체계 마무리** — 티켓 등급을 Graylog 설정에 맞춘 것까지는 했으나, 열린 티켓이 등급을 낮추지 못하는 점과 이벤트별 등급 기준을 더 다듬고 싶다.
2. **보안 이벤트 정리·보강** — 현재 탐지 규칙을 용도별로 정리하고, 빠진 공격 유형(예: IDS 연동 기반 탐지)을 추가하고 싶다.
3. **발표에서 못 보여준 부분** — 본인이 설정한 **n8n 접근 제한(5678 포트를 SIEM PC에서만 허용)** 등 보안 설정을 발표에서 충분히 보여주지 못해 아쉬웠다. 다음에는 이 부분도 시연에 넣고 싶다. (pfSense 망 구성 자체는 팀원 **서효상(SHS)** 담당이다.)

## 3. 느낀 점

처음에는 어떻게 완성될지 막막했지만, 각자 수업에서 배운 것을 바탕으로 맡은 부분을 해내고, 모르는 부분은 서로 물어보며 의견을 나눴다. 그렇게 웹,망,관제,자동 대응이 하나씩 연결되어 하나씩 연결되어 공격 한 번이 탐지부터 티켓과 알림, 등급별 대응까지 이어지는 것을 확인 했을 때,  혼자였다면 만들지 못했을 결과물이 팀으로 완성되었다는 점이 가장 인상 깊었다.

다만 내가 맡은 n8n 자동대응에 집중하느라 다른 파트에는 관심을 많이 두지 못했다. 다른 사람의 작업을 더 깊이 이해하며 임했다면 프로젝트에 더 기여할 수 있었고, 얻어 가는 것도 더 많았을 것이다.

진행하며 생긴 인증서나 방화벽 설정 등의 오류를 하나씩 해결할 때는 뿌듯했다. 하지만 문제를 파악하고도 시간 안에 끝내 고치지 못한 부분도 남았다. 이 부분을 마저 해결해 포트폴리오를 더 완성도 있게 다듬을 계획이다.
